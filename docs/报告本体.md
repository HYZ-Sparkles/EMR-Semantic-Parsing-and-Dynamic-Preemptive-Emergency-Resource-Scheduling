1.2软件功能
该软件包含病情输入和标定、患者分配和治疗以及前端信息展示的功能。
病情输入：在前端使用输入框实现，通过通信传递患者信息到后端。
病情标定：将病情描述通过字典树解析，按照危险分参考表得到患者对应的危险分数、所需要的医疗资源和治疗时间。
患者分配：先分配到需要的医疗资源，或者尝试抢占医疗资源。如果患者危险分不高，则进入大顶堆开始排队。
病人排队：排队中的患者存放在大顶堆中，大顶堆按照病人的危险分进行排序，分数越高位置越前。同时排队时间越长，病人危险分数越高(患者恶化)。
时间步长模拟：在调度器中设置时刻属性，模拟治疗患者的恢复和等待患者的病情恶化。
排队前端展示：左上面板“患者信息输入”区中的患者点击“登记”后如果需要的医疗资源已满且患者相对轻微，则进入大顶堆；中列的“急诊排队实时看板”实时显示排队情况。
事件日志展示：右下面板“事件日志”按 9 种类型着色徽章展示最近 30 条：arrive(入队，主色蓝)、pending(登记延迟到达，info 青)、assign(分配资源，success 绿)、preempt(抢占，danger 红)、suspend(被挂起，danger-2 暗红)、resume(恢复，info 青)、finish(完成，次级灰)、deteriorate(恶化，warning 橙)、reject(拒收，主色蓝)。
医疗资源治疗情况展示：右上面板“医疗资源状态”按资源种类分四段：抢救室(3 台)、CT 室(2 台)、手术间(2 台)、超声室(1 台)，共 8 个槽位。每台资源卡片有三种状态：空闲(绿色底，文字“空闲”)；治疗中(黄色底，显示当前患者姓名与“治疗剩余 tick / 总 tick”进度条)；被抢占(红色底 + 1.2s 呼吸边框闪烁，显示“抢占自：<被抢走患者姓名>”以及挂起名单)。
前端控制仿真：中列下方“控制台”提供 4 个动作：启动/暂停仿真；手动 +1 tick(单步推进)；清空(重建调度器)；步长下拉(0.5s/1s/2s/3s/5s 5档)。工具条右端实时显示 4 项统计：队、在治、挂起、已完成的人数。

1.3设计思想
- 软件的实现思路
软件的实现我采取的是“先前端后后端”的方向。前端是最终呈现给甲方的软件，因此在设计前端的接口时可以了解到所有软件的功能，给后端的实现提供方向。而假设先实现后端，那么前端在视觉上设计就被后端接口限制，并且可能出现前端接口不全，又需要进行后端接口更新的麻烦。
具体实施步骤：我先阅读了Vue 3官方文档与 Element Plus 组件 API，明确输入框、表单、标签、单选组、按钮、消息提示等控件的使用方式；而后搭建前端骨架，确定三栏布局，按左-中-右分别放置患者信息录入与参考表区、排队与控制区、资源与日志区；编写各组件的模板、响应式数据、props 通信契约，得出“前端需要后端提供的 8 个 HTTP 接口 + 1 个 WebSocket”接口清单；之后，我设计数据结构与算法，依据接口清单手工实现字典树(HashMap<char, TrieNode>)解决多模式串匹配，实现带位置索引的大顶堆(Vec<Entry> + HashMap<id, idx>，各操作 O(log N))，定义8槽位资源表(3 抢救室 + 2 CT + 2 手术间 + 1 超声)；实现后端，先写核心的调度器(接受患者 / 接收随机患者 / 时间步前进 / 分配医疗资源 / 抢占医疗资源)，再暴露对应路由 + WebSocket 广播，最后用异步方式的main启动仿真；软件完成后的调试使用curl端到端跑通测试脚本，再回到浏览器验证实时看板、事件日志、控制台的交互。
- 算法设计流程
算法主要是在后端隐性完成，因此算法设计模块在后端代码中完成。主要的算法包括：语义分诊评分算法、时间步长模拟算法、抢占与恢复算法。
语义分诊评分算法：与病情标定功能相配合，使用字典树解析患者的病情描述，计算患者的危险分数。
时间步长模拟算法：
    1. 模拟医疗资源的治疗过程，患者缓缓恢复健康。
    2. 随着在队列中等待的时间拉长，重症患者的病情可能会“自动恶化”(权重定时增加)，动态更新大顶堆。
    3. 治疗完成的医疗资源进行挂起列表的患者分配和大顶堆的患者分配。
抢占与恢复算法：
    1. 资源抢占：医疗资源对应的数据结构增加挂起列表属性，当危险分数更高的患者到来时抢占所需医疗资源中危险分数最低的患者所在的位置，并将该患者挂起在该医疗资源的挂起列表中。
    2. 恢复治疗：某个医疗资源完成治疗时，优先从该资源挂起列表中最危险的患者进行恢复治疗。如果挂起列表为空，则从大顶堆弹出患者进行治疗。

1.4逻辑结构与物理结构
逻辑结构是数据元素之间的抽象关系，体现在软件的模块划分、算法逻辑上。物理结构是数据元素在计算机存储器中的表示和映像，体现在软件具体的目录结构、编程语言、操作系统上。
- 逻辑结构
[图1.4.1 逻辑结构示意图]
软件包含4个模块：前端表现层、接入层、仿真调度核心层、数据结构基础层。
前端表现层使用三列布局，第一列是患者信息录用区和医疗词汇危险分数参考表，方便医生录用患者信息或者患者进行预约到院。患者的危险分数使用字典树对患者的病情表述进行扫描得到。第二列由“急诊排队实时看板”与“仿真控制台”组成：实时看板在WebSocket每帧推送时按score降序刷新当前队列，队首以左侧色条与背景色高亮；控制台通过按钮分别调用对应接口，并实时显示队、在治、挂起、已完成的患者个数4项统计。第三列由“资源状态网格”与“事件日志”组成：资源网格按种类分四段显示8个槽位的状态，颜色随state切换(绿/黄/红闪烁)；事件日志按9种类型着色徽章展示最近30条，倒序显示时间、类型、患者与详情，方便操作员追溯每个时间步的调度过程。
接入层负责前后端的通信，统一了前后端的接口。接口分两类：GET/WS方法接口：GET /api/snapshot 返回调度器完整状态，GET /api/terms 返回19个医学词汇的对应信息，GET /ws 升级为WebSocket，客户端订阅广播通道后即可在每次调度器推进时收到一份最新数据。POST方法接口：POST /api/parse {text} 传入患者的病情描述，返回匹配词、危险分、所需医疗资源；POST /api/admit 传入患者名字、病情、预计到达时间，返回患者分析后信息和事件描述；POST /api/random_admit 随机生成患者并录入信息；POST /api/tick 手动推进1个时间步；POST /api/auto 切换自动仿真；POST /api/reset 清空所有状态。手动推进时间步与自动推进时间步循环都走同一个step_and_broadcast工具函数，确保两条路径不会矛盾。
仿真调度核心层即调度器结构，包括4个主要功能。一、接收新患者：患者在信息输入之后，先解析主诉，若主诉中没有任何医学关键词则产生“拒收”事件且患者不入队；若是预约(预计若干时间步后才到来)则登记到预约列表并产生“延迟到达”事件，待仿真时间步推进到约定时刻时再物化入堆；若是直接到院则立即入堆并尝试分配医疗资源。二、仿真时间步：每推进一个时间步，依次处理“到点的预约患者入堆”→“在队和被挂起的患者按等待时长恶化加分”→“在治资源的剩余时间减少”→“治疗完成的资源释放后优先恢复被挂起者”→“重新尝试给队首分配资源”，每个时间步末尾把本次事件追加到事件列表并裁剪到最近30条。三、分配医疗资源：先按推荐类别查找同类空闲资源，找到则分配并产生“分配”事件；找不到则按同类在治患者中危险分最低者作为被抢占者，若新到者危险分比被抢占者高3分以上则触发抢占(产生“抢占”和“挂起”两条事件)；仍找不到则留在堆里等待恶化或新资源释放。四、生成前端页面的信息：把当前仿真时刻、当前队列、所有患者、全部医疗资源、最近事件、自动仿真状态、时间步长等打包成一份数据，通过广播通道推送给所有前端页面。
数据结构基础层是软件的基石，主要包括：一、医疗词汇枚举：医疗资源种类4类(抢救室/CT/手术间/超声)，19个医学词条按四档组织——致命级16-20共7个(例如心脏骤停、室颤等)、重症级10-15共5个(例如休克、呼吸困难等)、中等级5-9共4个、轻症1-4共3个。二、危险分计算的字典树：用哈希表存子节点，每个词条结尾处打终止标记并记下累计危险分；同一位置只取首个命中词，按起始位置、结束位置、危险分从高到低排序后去重。三、患者排队的大顶堆：用数组存所有患者条目，并配套一个哈希表记录每个患者在数组中的下标位置，使插入、弹出、按id删除、按id改分等操作全部为O(log(n))复杂度；分数相同时按到达时刻升序排队(先到先出兜底)。四、医疗资源状态表与挂起列表：共8个槽位，每槽位记录当前状态(空闲/治疗中/被抢占)、当前患者id、当前患者危险分、抢占者id、被抢占的原患者id、被挂起者列表、本次治疗剩余时间、本次治疗总时间；恢复时按当前危险分最高、同分取最晚被抢占者的规则从挂起列表中选人。

软件运行时只有一个调度器进程，由异步方式的main入口启动一个异步运行时，在其中并行跑两类任务：一类是HTTP与WebSocket服务(监听7878端口，路由表包含8个HTTP路由和1个WebSocket路由)；另一类是自动时间步循环(每200毫秒轮询一次自动仿真开关，若开启则再按用户设定的时间步长等待，到点后推进一格并广播快照)。进程内所有任务通过读写锁共享同一份调度器状态；每推进一格后就把当前快照通过广播通道同时推送给所有浏览器页面。前端Vite启动第二个Node进程：开发服务器监听5173端口，把前端对后端的接口请求与WebSocket连接反向代理到7878；浏览器作为第三个角色(数量任意)打开 http://localhost:5173 加载单页应用，通过WebSocket与HTTP代理与后端通信。
后端进程对外暴露7878端口，同时承担普通的HTTP接口和WebSocket长连接(同一端口由路由表按请求类型分发)。前端Vite开发服务器暴露5173端口，把前端对后端的接口请求反向代理到后端的7878端口、把前端的WebSocket连接也反向代理到后端的7878端口(由Vite配置文件中的代理规则处理)。因此用户只需访问 http://localhost:5173 即可：前端的静态资源由Vite直接提供(含热更新)，前端与后端的通信经代理透传到7878。生产环境可将前端打包产物挂在任意静态服务器，并把对后端的接口请求与WebSocket连接反向代理到7878即可。

1.5开发平台
代码的开发平台是vscode，前端使用Vue3，后端使用Rust完成。
前端技术栈：核心框架采用Vue 3，配合Element Plus组件库实现输入框、表单、按钮、消息提示等界面元素；构建与开发采用Vite，由Vue插件将单文件组件编译为浏览器可执行的JavaScript代码；启动脚本支持开发模式、生产构建、本地预览三种场景。第三方开源代码方面：使用浏览器原生WebSocket接口实现前后端长连接(含1/2/4/8/10秒指数退避重连)；使用浏览器原生fetch接口封装统一的请求函数，校验HTTP状态码后再解析响应；借助Vite内置的开发服务器反向代理把前端对后端的接口请求与WebSocket连接转发到后端，避免开发期跨域问题。组件通信方式：父组件向子组件传值用props，子组件内用defineProps接收声明；子组件向父组件传值用自定义事件@event。开发期不引入TypeScript、不引入Pinia/Vuex等状态管理库，单页应用+一个根快照变量已能覆盖全部状态管理需求。
后端技术栈：核心语言采用Rust，代码以模块为单位平铺拆分。Web框架选用支持WebSocket与宏特性的axum，由异步方式启动HTTP与WebSocket路由，路由表由统一的组装函数集中管理。异步运行时使用tokio承担Web服务与自动时间步循环两类异步任务。进程内多任务间通过读写锁共享同一份调度器状态，相比标准库的读写锁能获得更细粒度的并发控制。请求与响应通过serde与serde_json完成自动序列化，所有路由请求体、响应体、事件、患者、资源槽等数据结构都通过派生宏自动生成序列化代码。患者id使用uuid库的v4版本生成，确保每个患者的标识几乎不可能重复。随机患者功能使用rand库抽取词条与姓名。日志系统使用tracing与tracing-subscriber，通过环境变量控制日志输出级别。
软件运行环境：开发与测试均在Windows 11上完成(rustc 1.95.0、cargo 1.95.0、Node.js v24.11.1、npm 11.7.0)。Rust + Tokio 与跨平台无绑定，本项目可直接在macOS/Linux通过cargo run启动；npm与Vite同样跨平台。浏览器：任何支持ES2020与WebSocket的现代浏览器(推荐Chrome/Edge最新版，F12的Network/Console/WebSocket三个标签页用于调试)。
启动方式：
终端1：`cd backend && cargo run`
首次会下载约 200MB 的依赖并编译，启动后日志输出`EMR Scheduler listening on http://0.0.0.0:7878`；
终端2：`cd frontend && npm install && npm run dev`
首次安装约150MB依赖，启动后Vite提示`Local: http://localhost:5173`；浏览器访问 http://localhost:5173 即可。运行时拓扑：1个emr_scheduler进程(后端7878)+1个Vite进程(前端5173)+N个浏览器标签页(共享同一份调度器状态)。
生产环境可关掉Vite，改由`npm run build`产物挂在Nginx/Apache等静态服务器，并把 /api 与 /ws 反向代理到7878。

按上表案例(1.6.3)实际运行结果如下，全部在浏览器 http://localhost:5173 上验证：
P1 王伟“心脏骤停”——字典树命中“心脏骤停”(20)单条，累计20分，取其推荐类别为抢救室；患者立即入堆后由“尝试分配”步骤找到空闲的抢救室-1，产生“入队”与“分配”两条事件(队列看板瞬时出现#1 王伟20分随后清空；事件日志出现分配；资源卡抢救室-1由绿变黄，进度条7个时间步)。
P2 李芳“胸痛伴呼吸困难”——命中“胸痛”(13)与“呼吸困难”(14)共27分，取呼吸困难(14)的推荐类别为抢救室，分配到抢救室-2，进度条9个时间步；事件日志出现分配。
P3 张军“腹痛伴呕吐”——命中“腹痛”(9)与“呕吐”(4)共13分，取腹痛的推荐类别为超声室，超声室(仅1台)被P3占用，13/3=4个时间步。
P4 陈静“呕吐”——单条命中4分，推荐类别为超声室。此时超声室被P3占据、按推荐类别查找空闲资源返回空、按同类在治患者中找最低危险分槽位选P3(13分)作被抢占者，但4>13+3=16不成立，P4进入大顶堆等待。推进2个时间步后P4触发“恶化”+1分，危险分变5；再等2个时间步变6；按每2个时间步加1分的恶化规则不断累加，直到大于P3危险分加3分即16仍需要若干时间步。
P5 杨洋“咯血+昏迷”共26分，取昏迷的推荐类别为抢救室。此时抢救室-1(治疗P1，剩余时间步减少中)与抢救室-2(治疗P2，已治疗一段时间)都被占，按推荐类别查找空闲资源返回空；按同类在治患者中找最低危险分槽位在两个抢救室中选分数最低者(25或27)。若P5危险分26大于被抢占者危险分25加3即28不成立则P5进堆等待；只有在P1与P2治疗结束后P5才能直接分配，不会发生抢占——这与表中“与P2抢占同一抢救室”的预期现象不一致，是本系统当前抢救室数量较多场景下的实际行为。
P6 黄娜“无医学词”——字典树扫描命中0条，登记走拒收分支，事件日志出现拒收事件“未识别到医学关键词，请补充主诉描述”；前端同步弹出警告提示。
P7 赵敏“脑卒中”——命中“脑卒中”(17)，推荐类别为CT室；预计3个时间步后到达走延迟到达分支，事件日志出现延迟到达事件(说明将于3个时间步后到达)，3个时间步后由延迟到达物化步骤入堆，产生入队事件并尝试分配CT-1(CT共有2台空闲)。
批量“随机患者”——连续点10次，随机患者录入从19个词条随机抽2-3个用“并伴随”拼接、从10个姓氏与20个名字池中随机取名、0-5个时间步后到达，事件日志快速滚动，可观察持续恶化不断抬高危险分直至触发抢占。
综合上述案例，本系统能正确识别医学关键词(拒收路径生效)、按字典树累计得到危险分、给出正确资源建议、按危险分降序排队、按阈值+3分抢占，并在每个时间步推进在治资源、结束治疗、恢复挂起者、再分配——形成“识别→评分→排队→分配或抢占→治疗→释放→恢复”的完整闭环。

   右上面板“医疗资源状态”按种类分四段：抢救室(3台)/CT室(2台)/手术间(2台)/超声室(1台)，共8槽位。单台卡片有三种状态：绿色idle(空闲)；黄色busy(治疗中，显示当前患者姓名+治疗剩余tick/总tick进度条)；红色preempt(被抢占，1.2s呼吸边框闪烁，显示“抢占自：<被抢走患者姓名>”与挂起名单)。卡片表头以3个小圆点(绿/黄/红)做图例。

6. 高危患者的抢占，治疗完成后挂起患者的恢复
   当一名高危患者到来(且同类别资源无空闲)时，若新到者危险分比被抢占者高3分以上，则发生抢占：事件日志连续出现“抢占”和“挂起”两条；资源卡变红闪烁；被抢占者的姓名出现在“抢占自”行；被抢占者的剩余治疗时间与总治疗时间写入该槽位的挂起列表。治疗完成后，优先恢复挂起者中“当前危重分最高”者(同分取最晚被抢占者)，事件日志出现“恢复”行；列表为空则由“尝试给队首分配资源”步骤从大顶堆取队首。

第二部分 实践总结
2.1.所做的工作
本课程设计完成了“电子病历语义解析与急诊医疗资源动态抢占调度”系统的全栈实现，按“先前端后后端”的方向推进。
(1)前端骨架：确定三栏布局的样式；六个组件(录入区、参考表、排队看板、控制台、资源网格、事件日志)全部按单文件组件形式实现，每个组件内含模板、脚本与样式三部分；通过封装好的快照订阅函数获取后端快照，含1/2/4/8/10秒指数退避重连；输入框防抖250毫秒、提交按钮双击bug修改。
(2)接入层：暴露8个HTTP路由(解析、登记、随机登记、获取快照、手动推进时间步、切换自动仿真、清空、获取医学词典)和1个WebSocket路由；统一的“推进一格并广播快照”工具函数把HTTP手动推进与自动推进时间步循环统一到同一条路径。
(3)数据结构基础层：手工实现字典树、带位置索引的大顶堆、8槽位资源表(3抢救室+2CT+2手术间+1超声)；三模块均带单元测试。
(4)调度核心：实现患者登记、随机患者登记、物化入堆、时间步推进、尝试给队首分配资源、抢占、从挂起列表选人等功能，覆盖“接收(立即/预约/拒收)→入堆→恶化→推进治疗→释放→恢复挂起者→重试分配”完整闭环；抢占阈值设置为新到者危险分比被抢占者高3分以上，避免无意义抖动。
(5)仿真循环：以200毫秒轮询自动仿真开关、按用户设定的时间步长(200~10000毫秒区间)推进。
(6)文档与测试：学习笔记沉淀Rust/前端/算法三块学习心得与“改进想法”列表；流程图材料沉淀逻辑结构与物理结构图；README提供4个curl端到端脚本；cargo test共11个单元测试全部通过。
2.2.总结与收获
通过本次课程设计，在自我学习能力方面有四点提升(详细可看 ./docs/学习.md)：
(1)Rust所有权与生命周期——典型地遇到trait派生宏要求字段自身实现对应trait、'static既可作引用生命周期又可作泛型约束等概念；调度器用异步读写锁在多任务间共享状态；Axum的状态提取兼具“元组结构体解构”与“从路由状态中取应用状态”的双重含义；读写锁块作用域尽量小(推进一格并广播工具函数走“加锁推进→释放锁→加锁生成快照→释放锁→广播”路径)，避免长期持锁导致时间步循环卡顿。
(2)前端从“会用jQuery”到理解Vue 3响应式与编译产物——单文件组件的脚本块自动补全默认导出；事件绑定是事件监听的语法糖；Vite的“开发代理+热更新+生产构建”三件套理解：开发时启动5173，把前端对后端的接口与WebSocket连接代理到7878避免跨域；生产构建输出静态文件可直接挂Nginx；CSS变量+媒体响应+id/class/标签的层叠优先级使全站配色只需改一处根选择器。
(3)算法设计与复杂度分析的工程化——字典树用空间换时间解决多模式串匹配；位置索引的大顶堆把“按id改分”也压到对数级复杂度；资源表用“找空闲”与“找同类最低危险分”两个线性于同类槽位数的查找支撑抢占决策。
(4)网络与并发——WebSocket的广播发送器是一对多推送的天然选择；自动时间步循环以200毫秒轮询开关与按时间步长等待避免了“独占锁”问题；前端WebSocket断线触发指数退避(1/2/4/8/10秒)，让用户在网络抖动时也能看到状态自愈。
除了以上纯知识点的收获，本次软件开发也是我第一次结合社会需求进行的编程，让我意识到原来生活中我从来不会注意的医院挂号排队程序也会有这么复杂的逻辑，而且，程序员也应该拥有善于发现需求的眼睛，为了将世界变得更加便利和高效尽一份力。
